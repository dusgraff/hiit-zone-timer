# TLDR

TLDR is a hierarchical index of the entire repo, built for quick lookups. It works like a table of contents in a book: each folder has a `.tldr.md` that summarizes what's in it and links down to its subfolders' `.tldr.md` files. Any model, even in a fresh chat, can walk down from the root to the context it needs without searching through files.

## Intent

- **Token efficiency.** Get to information as quickly as possible without spending tokens searching and sorting through files. Keeping the TLDRs current costs some tokens, but it saves more in the long run.
- **Cold starts.** The user can open a brand-new chat and just start talking. Claude starts from the root CLAUDE.md and `.tldr.md`, then works down through the TLDR files to the information the question needs, with no other setup or explanation required.

## Files

| File | Where | Purpose |
|---|---|---|
| `.tldr.rules.md` | Project root only (exactly one) | This rules file. |
| `.tldr.ignore` | Project root only (exactly one) | Items the tree skips entirely, in `.gitignore` syntax (see rule 9). |
| `CLAUDE.md` | Every managed folder, plus the top folder of each disabled branch (to carry the disabled marker) | Imports this rules file, enabled or disabled (see Markers). That's its only TLDR job. It may also hold folder context (see rule 2). |
| `.tldr.md` | Every managed folder | What's *in* the folder. One short entry per file or subfolder (excluding TLDR files, see rule 2), with links down to subfolders' `.tldr.md` files. |

TLDR files are never imported, so they're only loaded when needed.

## Lookups

**Walk the tree before searching.** When Claude needs context it doesn't have, it walks the TLDR tree. That covers an unfamiliar name, a question about the repo, or anything that seems to be missing.

- **Start at the root `.tldr.md` and go down.** At each level, read the Scope and Contents and pick the branch most likely to hold the answer. If a branch turns out to be wrong, back up and try another.
- **Don't search for files the tree indexes.** Grep, glob, and file search are fallbacks, used only after the tree is exhausted. They're also fine for things the tree doesn't cover, like searching for text inside files or looking in disabled folders.
- **Fix the tree when it fails.** If the walk should have led somewhere and didn't, update the `.tldr.md` entry that sent Claude the wrong way.
- **Don't walk without a reason.** If the context is already loaded, or the task doesn't need repo knowledge, skip the walk.
- **Open TLDR files by direct path** (`<folder>/.tldr.md`). Many search tools skip dotfiles, so they won't reliably turn up in a search.

## Markers

Every CLAUDE.md points to this rules file with a relative-path import, so the rules are always in context. The flag after the import decides the state:

- **Enabled:** `@../.tldr.rules.md`
- **Disabled:** `@../.tldr.rules.md --DISABLED`

Use one `../` per level below the root. Claude Code still imports the file on a `--DISABLED` line. The flag is what turns management off.

The import line goes at the very top of the CLAUDE.md: line 1, or directly below the title heading if the file has one.

## Rules

1. **Every managed folder gets both files.** When a new folder is created, add a `CLAUDE.md` with the enabled marker and a `.tldr.md`.
2. **Keep TLDRs current.** When a file or folder is added, renamed, or removed, update the parent folder's `.tldr.md` in the same piece of work. Entries follow rule 8's Entry detail. TLDR files don't list TLDR system files (`.tldr.md`, `.tldr.rules.md`, `.tldr.ignore`), a CLAUDE.md that holds only the import line, or anything matched by `.tldr.ignore`. When a folder's Scope changes, check the parent's entry for that folder and update it if it's no longer accurate.

   **CLAUDE.md with content.** A CLAUDE.md can hold more than the import line. Use it for what should always be in context when working in that folder. When it does hold content, list it in the folder's `.tldr.md` like any other file. 

   **Claude owns the `.tldr.md` files.** Claude never asks permission to update them. They're the repo's memory. Whenever something changes, or an entry is missing, wrong, or vague, Claude fixes it in the same piece of work.

   - **Subagents** update `.tldr.md` for their own changes by default.
   - **The main session can tell subagents not to touch it,** usually when several run in parallel in the same folder and would overwrite each other's edits. In that case, the main session updates the `.tldr.md` as soon as they finish.
   - **No "needs an entry" notes.** A subagent that can't update the file lists the files it added or changed in its final report, and the main session makes the update. It never leaves that note in its output files.
3. **Disabling.** A folder's CLAUDE.md uses the disabled marker. Disabled means Claude does not manage TLDR files there. Other notes may follow (e.g. "only read contents as needed or as directed"). Only the user disables TLDR, either by hand or by telling Claude to. A disabled folder has no `.tldr.md`. Its parent still lists it, linking to the folder itself (`[name/](name/)`). The entry says what the folder holds, like a one-line Scope, and ends with "TLDR disabled." Lookups that need something inside it fall back to searching.
4. **Inheritance: nearest marker wins.** A folder is managed unless it or an ancestor has the disabled marker. A deeper CLAUDE.md with the enabled marker re-enables it from that folder down.
5. **Large discovered trees: ask first.** If Claude finds an existing folder with a large tree under it (more than about 20 items in total, or more than two levels of subfolders), it does not index it automatically. It tells the user and asks whether to index the whole thing, disable TLDR there, or handle it another way.
6. **Rules changes need user approval.** Claude never changes the rules in this file on its own. The Loose ends section is exempt: Claude adds and removes items there freely. If a change seems worthwhile, Claude proposes it ("I think changing the rules to X would make sense") and waits for a clear yes, unless the user directly says to update the rules now.
7. **Check every rules change.** Once a rules change is made, Claude runs a loose-ends-and-consequences check and reports it to the user. The check asks:
   - Is the new wording clear and unambiguous about how the rule works?
   - Does it conflict with or overlap any existing rule?
   - What does it affect in the existing tree (for example, rework of existing CLAUDE.md or `.tldr.md` files)?

   Any open questions go into Loose ends.
8. **`.tldr.md` format.** Each `.tldr.md` has two sections:
   - **Scope:** a brief statement of what goes in this folder (and, if useful, what doesn't). Claude uses it to decide where new files belong without being told.
   - **Contents:** a bullet list, one entry per item: `- [name](link) — short description`. Subfolder entries link to that subfolder's `.tldr.md` (disabled folders: see rule 3). Use "No items yet." when the folder is empty.

   **Entry detail.** An entry answers one question: does this item need to be opened? Keep it to one line, with just enough to decide:
   - what the item is and what it covers (its topics, or the questions it answers)
   - facts that help tell items apart, like dates, status, or which project it belongs to

   Don't summarize what the item says, such as its findings, conclusions, or results. That's what opening the file is for. If two entries could be mistaken for each other, add the detail that tells them apart.
9. **Ignored items.** `.tldr.ignore` lists items nobody would open for their content: OS metadata, version-control and tool folders, caches, build output, installed dependencies, and the like. It uses `.gitignore` syntax. Ignored items get no entry in any `.tldr.md`, and ignored folders get no CLAUDE.md or `.tldr.md`. This is different from disabling (rule 3): a disabled folder holds real content and is still listed in its parent; an ignored item is invisible to the tree. When Claude finds something that looks like an ignore candidate, it asks the user ("Found X. I think it's an ignore candidate. Add it?") and adds it only on a yes. `.tldr.ignore` is separate from `.gitignore`: git may ignore content worth indexing (private data, secrets), and the tree may skip files git tracks.
